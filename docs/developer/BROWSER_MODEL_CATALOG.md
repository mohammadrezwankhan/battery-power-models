# Embedded browser model catalog

> Documentation snapshot: **2026-11-19**. Implementation examined: [`0304bfec25c43f42f103ebda239749b88609a187`](https://github.com/mohammadrezwankhan/battery-power-models/tree/0304bfec25c43f42f103ebda239749b88609a187). Execution evidence and proposals are identified separately.

The inline `LabSimulation` library ships ten deterministic teaching modes. The active config in this repository selects **`thermal`**. The other modes are exported implementation surface, not evidence of ten native battery/power solvers or ten independently validated scientific applications. This catalog accounts for them without extending their scientific claims. [Library specifications and implementations](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/docs/index.html#L148-L338), [selected mode](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/docs/lesson-config.json#L128-L134).

## Shared contract

`getModelSpec(kind)` returns the declared specification or throws for an unknown kind. `resolveParameters` considers only keys in that specification, clamps finite numeric values to each range, and substitutes defaults otherwise. `evaluateModel` clamps time into the declared horizon (nonfinite time becomes zero). Each result is a flat object of the metric keys below. The exact parameter names, default values, ranges and labels are exposed in `MODEL_SPECS`; treat them as snapshot-specific interfaces. [Resolver and evaluator](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/docs/index.html#L232-L320).

## Selected explanatory relationships

For `battery`, SOC is clamped from `SOC_0 − 100 I t_h / capacityAh`; loaded voltage is the illustrative `320 + 0.8 SOC − I_effective R`. This is a teaching curve, not a measured open-circuit-voltage map. For `degradation`, the decay coefficient is `fadePer1000Pct/100000 × exp((temperatureC−25)/20) × sqrt(cRate)`, with retention `100 exp(−k cycles)`. Parameter names express the library's heuristic, not a fitted manufacturer rating. [Branches](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/docs/index.html#L244-L280).

For `control`, the implemented response corresponds to a zero-initial-state second-order system driven by a step: `y'' + 2ζω y' + ω²y = Kω²r`. The code branches on damping and uses a narrow near-critical comparison; the displayed error is relative to the input setpoint, while overshoot is relative to the gain-scaled target. For `charging`, the model's transition and time constant are derived from the remaining 20% capacity and effective charger power. These explanations are source interpretations of the teaching formulas, not additional algorithms. [Control through charging branches](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/docs/index.html#L291-L320).

## Verification boundary

The existing automated browser suite verifies CSP/document contracts. Native Python/MATLAB tests exercise native models and parity fixtures; they do not automatically establish all ten browser modes' numerical correctness. The documentation audit separately evaluated all eight configured thermal lesson checkpoints against the actual exported library. That bounded check concerns the selected thermal lessons only. Expanding executable browser-model invariants and export/state tests is proposed in [the roadmap](../../ROADMAP.md).

The animation archive's `waveform.html` has a separate illustrative damped/oscillating visual calculation; it is not a public alias of a native thermal/DC-link implementation. [Archive script](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/docs/animations/waveform.html#L154-L215). Its historical explanatory role should remain visible when linking it from a portfolio.

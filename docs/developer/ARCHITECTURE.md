## Execution boundaries

| Component | Inputs and state | Output and boundary |
|---|---|---|
| `src/battery_thermal.py` | Finite current sequence; uniform interval; constant thermal parameters; optional initial temperature | Initial temperature plus one temperature per interval; optional native CSV through a separate writer |
| `src/dc_link.py` | Ideal triangular-current ripple inputs or constant-power pulse inputs | Two independent scalar sizing relationships; no converter transient simulation |
| `matlab/*.m` | Equivalent numeric arguments; MATLAB thermal inputs are a row vector and optional struct | Thermal row vector or a two-field DC-link struct |
| `docs/index.html` | Embedded lesson config and a deterministic JavaScript teaching library; in-memory UI state | Canvas, metric cards, checkpoint comparisons and synthetic CSV; does not execute Python or MATLAB |
| `docs/native-lessons.html` | Embedded historical native-lesson catalog | Search, filtering and copyable commands; no native execution |
| `docs/portfolio/index.html` | Embedded four-path learning plan; browser-local notes and completion state | Source links and downloadable study-plan JSON; no native execution |
| CI and maintenance tools | Source checkout, manifests, tests, scanner contracts and CI event metadata | Test/security reports, provenance checks, Pages artifact and policy conclusions |

## Native data flow

`ThermalParameters` supplies four constants. `simulate` validates the initial state and interval, then applies `analytical_step` to every current interval. `constant_profile` creates a count of equal-current intervals; the CLI divides the requested duration by that count before simulating. `write_csv` validates the complete trace before opening the destination. DC-link functions are independent of the thermal state and of each other. [Thermal flow](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/src/battery_thermal.py#L59-L138), [DC-link functions](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/src/dc_link.py#L9-L44).

There is no coupled electrical/thermal state estimator, battery state-of-charge solver, controller, measured-data loader, database or service API in the native modules. A proposed coupling belongs in a separately reviewed implementation change with explicit units, provenance and tests; it must not be inferred from similarly named browser teaching modes.

## Browser data flow and persistence

The application reads an embedded JSON config, resolves four thermal parameter controls, and evaluates 241 uniformly spaced sample times from 0 to the configured 60-minute horizon. It draws the current trace and evaluates each lesson checkpoint at the checkpoint's own declared time. Playback advances model time faster than wall time and respects reduced-motion preference at initialization. The numerical library is exposed as `window.LabSimulation`; selected controller access is `window.LabDashboard`. [Configuration and setup](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/docs/index.html#L147-L160), [controller](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/docs/index.html#L339-L487).

Dashboard values and verification indicators live in memory. The portfolio page separately stores study notes, completed paths and motion preference in `localStorage` under a repository-and-source-revision key; its exported study plan says the guide did not execute the native models. The animation archive includes an illustrative waveform, not an additional native validation result. [Portfolio persistence/export](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/docs/portfolio/index.html#L284-L314), [archived waveform](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/docs/animations/waveform.html#L154-L215).

## Verification and publication boundaries

Python tests cover numerical properties and invalid inputs. Frozen parity fixtures contain Python baseline outputs; the MATLAB gate separately executes MATLAB and compares against both frozen fixtures and a fresh Python capture tied to Git HEAD. A successful Python fixture check alone is not a MATLAB run. [Fixture provenance](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/tests/fixtures/python_matlab_parity.json#L1-L18), [capture and verification](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/scripts/capture_python_parity.py#L1-L214), [MATLAB gate](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/tools/security_numerical_gate.m#L1-L116).

GitHub Actions deploys the existing `docs/` directory to Pages after its static validation job on qualifying main-branch pushes. The new handbook is a static derivative of Markdown and introduces no application endpoint or runtime dependency. [Pages workflow](https://github.com/mohammadrezwankhan/battery-power-models/blob/0304bfec25c43f42f103ebda239749b88609a187/.github/workflows/deploy-dashboard.yml#L6-L90). Review the [CI playbook](../maintainer/CI_CD_AND_RELEASE_PLAYBOOK.md) before interpreting any check as a delivery gate.
